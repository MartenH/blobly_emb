    blobly¶

    A V-language automotive software stack. No heap, sim-first, generated from one config, and proven on real silicon. It de-AUTOSARs the ideas that matter — a communication stack, network management, non-volatile memory, an IO layer, a secure bootloader, and on-target tracing — into a small, static, readable codebase.

    Get started → How-to guides →

    What it is¶

    One ecu.toml describes the ECU — its buses, signals, frames, function blocks, threads, cores, and IO points. A build-time generator turns that into static tables and freestanding C — no allocation, no reflection, no runtime config parsing. The same image runs on a host simulator (POSIX + vcan) and on an STM32 under ThreadX, so you develop and test on your laptop and flash the identical logic to the board.

    • :material-lan-connect: Communication

      A CAN-FD stack with TX modes, signal routing, ISO-TP and UDS — signals and frames declared in config and a DBC, encoded by generated codecs.

    • :material-sleep: Network management

      OSEK-style NM with sleep/wake, CBV, and NM-gated TX — bench-verified sleep choreography including an in-sleep NvM flush.

    • :material-content-save-cog: Non-volatile memory

      An NvM stack with wait-free access discipline and a boot/persist chain, verified on the H755.

    • :material-toggle-switch: IO

      GPIO, ADC (continuous-scan DMA), and PWM as ordinary signals — transport derived from topology. ADC + PWM are bench-verified on silicon with an on-target test.

    • :material-shield-lock: Secure bootloader

      A UDS bootloader with a signed-image boot chain (Ed25519), a TRNG-gated seed/key, and an ISO-14229 session lifecycle.

    • :material-chart-timeline: Tracing

      On-target thread/ISR/FB tracing dumped over CAN — single-core and multi-core, with a config-driven manifest the host decoder reads.

    Principles¶

    No allocation, ever

    Every buffer, ring, pool, and table is static and fixed-size. The no-alloc discipline is a build-time lint, not a convention.

    Sim-first, then silicon

    The host simulator runs the real stack over vcan; the bench (NUCLEO-H755ZI-Q and STM32H735G-DK) proves the hardware paths. Bench results feed back into the requirement traceability matrix.

    Requirements-driven

    Every capability is a REQ-*; tests and on-target checks declare what they verify, and make trace builds the coverage matrix — host and on-target contexts side by side.
