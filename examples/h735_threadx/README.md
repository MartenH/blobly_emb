# h735_threadx — a ThreadX target GENERATED from ecu.toml (P3c-1, phases 6a–6b)

The convergence phase: everything the hand-written [`threadx_h735`](../threadx_h735) proved,
now **generated by loom2v from `ecu.toml`**. This example has the *same* FBs, Loom, CpuLoad
telemetry, and `[trace]` as [`h735_app`](../h735_app) — only its `[target] kind` is
`"threadx"` instead of `"baremetal"`, and loom2v wraps the FB superloop in a real **ThreadX
thread** (created by a generated `tx_application_define`, paced by `tx_thread_sleep`) instead
of the bare-metal inline superloop.

**Trace (6b-1).** On the ThreadX target, `[trace]` engages the **exec-change-hook** recorder
(`trace_hooks.c`, driver-independent), not the bare-metal polled capture — the FB loop being
a real ThreadX thread means the hooks capture every context switch + ISR for free. The
generated FB thread is the **sole bus owner** (lock-free, no mutex): it sends telemetry *and*
streams the trace ring — snapshot-under-brief-freeze, then 16 records/pass only while the Tx
FIFO has room (no spin). Decode with `candump can0 | decode_trace.py` (raw per-record frames
on `record_id`).

```
make -C ../.. deps      # once: ThreadX + CMSIS
make flash              # st-flash the generated .bin
candump can0            # CpuLoad (0x7E0) + LoadDetail (0x7E1) + trace (0x7E5)
```

## What loom2v generates (`gen/loom_gen.v`)

For `[target] kind = "threadx"` the emitter adds, around the reused baremetal `run()` FB
superloop:
- the ThreadX API by **FFI decl** (`_tx_thread_create` / `_tx_initialize_kernel_enter` /
  `_tx_thread_sleep` — the real symbols; the public `tx_*` names are macros in `tx_api.h`,
  which is deliberately not included so its `strlen` can't clash with V's),
- a static TCB (opaque byte buffer ≥ `sizeof(TX_THREAD)`) + thread stack,
- a thread entry that opens the CAN channel and calls `run()`,
- `@[export] tx_application_define` that `tx_thread_create`s the app thread,
- `pub fn boot()` → `tx_kernel_enter()`, which `main.v` calls after the board bring-up.

The FB `run()` body is byte-for-byte the baremetal one except the pace-to-tick idle becomes
`tx_thread_sleep(1)` — the thread yields to the RTOS instead of busy-waiting, so the Loom's
load (= run-time / wall-clock) stays honest.

## Config → thread mapping

`h735_app`'s `ecu.toml` places all three FBs (Governor/Load/Heartbeat) on the **one** thread
`app_main`, so this generates **one** FB-scheduler thread — which is all phase 6a emits (the
ECU model still rejects a partition with more than one `[[partition.thread]]`, and this
emitter uses only that thread). Spreading FBs across several `partition.thread`s — one
ThreadX thread each, with the wait-free triple-buffer IOC (`threadx_h735/ioc.h`) carrying the
cross-thread signals — plus the FDCAN-Rx-ISR comm thread and the trace dump are **future
work (phases 6b/6c)**.

## Verified on the board

`make flash`, `candump can0`: the CpuLoad `0x7E0` (byte 0 = core-0 load in **percent** —
`encode_cpuload` divides the Loom per-mille value by 10, and the DBC labels the byte `%`) and
LoadDetail `0x7E1` frames stream, load tracking the FB work — the generated ThreadX target
boots, `tx_kernel_enter` creates the app thread, and the FBs run under ThreadX. Structurally
the generated counterpart of the hand-written `threadx_h735` (the golden reference).
