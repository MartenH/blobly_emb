# h735_app — FBs + Loom + telemetry on hardware (STM32H735G-DK), generated from config

**The one bare-metal target** (`[target] kind = "baremetal"`): every other on-target image is
ThreadX, so this is what keeps loom2v's single-core superloop emitter and its P3c-0 trace runner
built (CI's cross job), tested (`bench_test.sh`, run by `make hwtest`) and verified
(REQ-TRACE-001, `h735-app-baremetal-trace`).

The first example to run the **real stack on silicon, driven entirely by `ecu.toml`**:
application function blocks scheduled by the **Loom**, with the Loom's per-core
processor-load measurement streamed out FDCAN1 — watchable live in blobly_net. There
is no hand-written superloop; `loom2v`'s bare-metal target emitter generates it.

On top of the register-level FDCAN driver (`driver/can`), this proves the
layers above it — `loom` (scheduling + load accounting) and `comm/telem` (the load
codecs) — generated from config and running on the bare-metal M7.

```
ecu.toml ──loom2v [target]──▶ gen/ ports/ sig/ ─┐
app/*.v  (pure FBs) ────────────────────────────┼─ V -freestanding ─▶ app.c ─┐
main.v   (board init + gen.run) ─────────────────┘                            ├─ gcc ─▶ .bin ─▶ flash
boards/h735dk (clock, DWT timebase, pins, startup) ──────────────────────────┘
driver/can (-DBLOB_CAN_FDCAN)
```

## What it does

Three **pure, portable** function blocks run on one `loom.Scheduler` (single M7 core):

| FB | period | what |
|---|---|---|
| **Governor** | 100 ms | ramps a work command (`LoadCmd`, an LCG iteration count) as a slow triangle |
| **Load** | 1 ms | burns the commanded iterations of pure compute — the thing measured as load |
| **Heartbeat** | 100 ms | a cheap "still scheduling" counter |

The FBs touch no board or `osal` API, so the **same `ecu.toml` + FBs** can generate a
host/sim build too — the `[target]` block just selects the bare-metal emitter here.

Every 500 ms the generated superloop sends two frames:

- **`0x7E0` CpuLoad** — per-core load over the **1 s** window (byte i = core i; only
  core 0 moves on a single-M7 board).
- **`0x7E1` LoadDetail** — core-0 load over **three windows** plus overruns:
  `byte0` = load @ **100 ms** (fast, catches bursts), `byte1` = **1 s** (steady),
  `byte2` = **10 s** (trend), `byte3` = **overruns this period**.

The Governor breathes the command between ~20 % and ~40 % of the 1 ms slot, and every
512th Load run is a one-off ~550 µs spike (`iters_spike` in `app/fbs.v`): a mostly idle
core with a rare anomaly, which is what the trace trigger below freezes around.

The superloop is also the **trace runner** (`[trace]`, P3c-0 — docs/trace-multicore.md §5.0):
every FB dispatch is a record in a 64-entry ring, armed from boot, and a handler over 500 µs
freezes it (the flight-recorder trigger — the periodic Load spike trips it). A host drives it on
the same bus: **`0x7EC`** TraceCmd in, **`0x7ED`** TraceRsp out, the frozen window as an
ISO-TP block dump on **`0x7EE`** with flow control on **`0x7EF`** — the same protocol as the
host `trace_demo`, on ids that stay clear of the other system_full nodes sharing the bench's
compute bus (see the `[trace]` comment in `ecu.toml`). Handlers only: a polled superloop has no threads or ISRs to record.

## How it's generated

`loom2v` reads `ecu.toml`. The `[target] kind = "baremetal"` block selects a
**single-core emitter** that differs from the host path in three ways, all because a
bare-metal M7 has no threads and no POSIX:

- **no `spawn`, no `osal`** — one inline `run(ch)` superloop instead of spawned
  per-partition threads;
- **DWT timebase** — `board_now_us()` (the Cortex-M7 cycle counter) replaces
  `osal.now_us()`;
- **fixed 1 ms tick** — the loop idle-spins to a tick boundary between passes, so the
  time between scheduling passes is *real idle*. This matters: the Loom measures load
  as run-time ÷ wall-clock, so without a genuine idle gap an unpaced spin would read a
  bogus ~50 % floor (the host gets this idle from `osal.sleep_us`).

All of `gen/`, `ports/`, `sig/` are generated; never edit them. Only `app/*.v` and
`main.v` are this example's; the board bring-up, startup and linker script are
`boards/h735dk`'s (`board.mk`'s `BOARD_BSP_BARE` / `BOARD_LD_BARE`).

## Layout

| file | what |
|---|---|
| `ecu.toml` | the source of truth: partition, local signals, FBs+handlers, `[telemetry]`, `[target]` |
| `bus.dbc` | the telemetry frames (`CpuLoad` 0x7E0, `LoadDetail` 0x7E1) for tooling/decode |
| `app/*.v` | the three pure FBs (hand-written) |
| `main.v` | board init → `gen.run(ch)` (tiny platform seam) |
| `bench_test.sh` | the on-silicon trace check over SWD (`make hwtest`) |
| `gen/` `ports/` `sig/` | generated by `loom2v` |
| `Makefile` | `make` = generate → transpile → cross-compile; regenerates if `ecu.toml`, the FBs, *or* `loom2v` changes |

## Board specifics (STM32H735G-DK)

- **CPU clock**: `board_clock_init()` brings the M7 to **550 MHz** (Direct SMPS → VOS0
  → PLL1). ⚠️ The supply write must match the DK's solder bridges (SB2/13/20/21 = SMPS);
  a mismatch **browns out VCORE and locks the debugger** — recover with
  `st-flash --connect-under-reset`. The bring-up is `boards/h735dk/board.c`.
- **Timebase**: the Loom needs monotonic µs; bare-metal has none, so
  `board_timebase_init()` runs the **DWT cycle counter** and `board_now_us()` divides
  by the achieved CPU MHz (64-bit accumulated to hide the 32-bit ~7.8 s wrap).
- **FDCAN1**: `PH13` = TX, `PH14` = RX, **AF9**; HSE bypass 25 MHz kernel clock →
  **500 kbit/s classic**.

## Build & flash

```sh
make -C ../.. deps    # CMSIS headers into third_party/ (once)
make                  # generate + transpile + cross-compile -> build/app.bin
make flash            # st-flash write build/app.bin 0x08000000
BLOB_H735_SERIAL=<serial> ./bench_test.sh --flash   # flash + the trace check over SWD
```

The DK is system_full's sysnode board, and this image overwrites sysnode's bootloader at
`0x08000000`; reflash `examples/system_full/nodes/sysnode` afterwards for a system bench.

## Watch the load

Wire FDCAN1 CANH/CANL to a USB-CAN adapter (**500 kbit/s classic**, 120 Ω each end).
The adapter must be a **normal ACKing node** — a lone transmitter with no ACK goes
error-passive and the telemetry stalls.

```sh
candump can0
#  7E0  [8]  <load@1s> 00 ..            (CpuLoad, per core)
#  7E1  [8]  <100ms> <1s> <10s> <ovr> ..(LoadDetail: windows + overruns/period)
```

Live in **blobly_net**: `projects/h735-cpuload.blobnet` decodes both via
`dbc/cpuload.dbc` — plot `Load_Core0` (0x7E0) and the `Load_100ms/1s/10s` + `Overruns`
signals (0x7E1) to see the fast window lead, the 1 s smooth, the 10 s trend, and the
overrun pulse at each peak.

**✅ Confirmed on hardware** (STM32H735G-DK ↔ PCAN-USB Pro FD, 500 kbit/s): both frames
at 2 Hz; `Load_100ms` leads and spikes to 99 %, `Load_1s` smoothed, `Load_10s` the slow
trend, `Overruns` pulsing to saturation at the peak and back to 0 — the on-silicon
proof of the Loom's multi-window load measurement (REQ-TELEM-001) and CpuLoad reporting
(REQ-TELEM-002) running bare-metal, generated from `ecu.toml`.

## Notes

- **Polled, no ISR.** FDCAN Tx and the whole loop are polled; the vector table is all
  `Default_Handler` bar reset.
- **Warnings.** V's freestanding C emits benign 32-bit pointer-cast warnings from
  unused builtin syscall paths; the link is clean.
- **No COM bus bridge.** The bare-metal emitter refuses external (bus) signals; a node
  with bus signals, diagnostics or IO is a ThreadX target (`examples/system_full`).
