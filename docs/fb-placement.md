# FB placement — what an FB can do on each core

Moving an FB to another core of a node is its `thread` line in `ecu.toml`, nothing else
(REQ-INV-007). This page says what that holds for today and what it does not: one row per
capability, each a requirement in [`requirements/placement.toml`](../requirements/placement.toml)
(REQ-PLACE-*), so a gap is a requirement nothing verifies yet and shows in
[`traceability.md`](traceability.md). A move into a gap is **refused at generation, naming the
reason** until its route is generated — `tools/sysgen/fb_move_test.v` moves every FB of `system_full`'s two-core node and holds
each refusal to the list below. The open gaps are #424.

## Terms

- **Platform owner** — the core that brings the chip up: clocks, pins, peripherals, the shared
  window's handshakes, and releasing the other cores. On the H755 the CM7. One per node.
- **Satellite** — any other core of the node (the H755's CM4). It owns no clocks, pins or
  peripherals; its image is generated by the platform owner's run (`image = <dir>`).
- **Bus owner** — the core whose comm thread drives a bus: receives and decodes its frames, and
  encodes and sends them. Today every bus is owned by the platform owner (REQ-PLACE-012 is the gap),
  so a satellite reaches a bus only through it.
- **Crossing** — a signal whose writer and readers sit on different images. It follows the signal,
  writer's image to reader's, whatever the boot roles; "up" (satellite → owner) and "down" (owner →
  satellite) name the two directions on a two-core part ([xcore.md](xcore.md)).

## The principle: a crossing's endpoint is any context

An FB never calls a service; it writes or reads a signal, and the service — NvM's journal, the
parameter store, fault memory, the diagnostic server, the io thread, the eth thread, a comm thread —
is the other end, in ONE context on the core that owns it. So an FB on another core is the same
signal with a crossing inserted: the service's context reads the up channel the FB writes, or writes
the down channel the FB reads, exactly as the comm thread already does for a bus signal (it reads a
satellite FB's output to send it, and writes a received value down to a satellite reader). The
transport, its gate and its single-writer rule do not change; each service only names the context
it reads and writes in. Every gap below is a route of that kind not generated yet — not a limit of
the design — and the order they close in is: NvM and parameters (006, 007), then faults and DIDs
(008, 009).

An FB's source does not move either: a node's FBs are one `app` module, in the platform owner's
folder, which every image of the node compiles (each declares every FB's ports; the linker drops
the FBs an image does not host).

A node-internal signal may leave `from` and `to` out: they then follow the FBs that write and read
it, which is what makes a move one line. Written, they are checked against the FBs — a stale one is
refused naming both partitions, never generated wrong.

## The matrix

| capability | on the platform owner | on a satellite | requirement | evidence / gap |
|---|---|---|---|---|
| read a received bus signal — lean, or checked (deadline, E2E, SecOC) with its status and lost count | ✅ | ✅ | REQ-PLACE-001 | H755 bench 2026-11-05 (`system_full/test/xcore_domain.lua`: E2E, timeout and integrity seen on the CM4); `tools/loom2v/xcore_down*_test.v` |
| an FB's output read by an FB on another core, every lane type (bool, u8..u32, i8..i32, f32; u64, i64, f64 in two lanes) | ✅ | ✅ | REQ-PLACE-002 | bench: a two-lane u32 at 20/s, never torn; the other types compiled and round-tripped on the host only |
| one output read on its own core and another at once (fan-out) | ✅ | ✅ | REQ-PLACE-003 | bench: `HostLedLevel` on both cores; generator test for satellite → both |
| any number of crossing signals, bounded by the shared window | ✅ | ✅ | REQ-PLACE-004 | past the 4-slot pair pool a signal rides a wide channel, decided at generation |
| a signal written by an FB and sent on CAN | ✅ | ✅ | REQ-PLACE-005 | sent as an owner FB's is: on its period from boot, the initial payload until the first value, at the DBC's DLC (bytes past its lanes keep the initial payload); a satellite that stops repeats its last value, as a stalled owner FB does, and an absent or mismatched one (the layout gate shut) leaves the initial payload — liveness is an alive counter's or E2E's job on both cores |
| a persisted signal (persist = now / shutdown) written by an FB | ✅ | ✅ | REQ-PLACE-006 | the FB's thread keeps the cell and publishes it on an up channel, which the owner's journal service reads (behind the layout gate) in place of the staging cell; the restore goes down a channel before the satellite is released, seeding the cell before the first dispatch. An owner FB may not also read it (the journal is the channel's one owner reader). Bench: system_full's DynKept, latched on the CM4 and restored through a reset |
| a calibration parameter (`[[param]]`, 0x2E) read by an FB | ✅ | ✅ | REQ-PLACE-007 | `param_pub` — the one publish point, at the restore and on 0x2E — also writes a down channel (one lane per field); the satellite is released after the restore, so its first dispatch reads the restored value. Bench: system_full's DynLedCap, coded on the CM7 and applied by the CM4 |
| a fault (`[[fault]]`) owned by an FB — debounce, fault memory, 0x19 / 0x14 / 0x85 | ✅ | ❌ | REQ-PLACE-008 | route: the test result up to the owner's debounce and fault memory (the 0x85 / 0x14 control stays there). Today's workaround: the satellite FB writes its result as a bool signal and an owner FB owns the fault. A signal-status fault on a signal a satellite FB reads works. |
| a live DID, or a fault snapshot, on a value an FB produces | ✅ | ❌ | REQ-PLACE-009 | route: the diagnostic refresh reads the up channel (the comm thread already polls the values it sends) |
| an io point (GPIO, ADC, PWM) read or written by an FB | ✅ | ❌ | REQ-PLACE-010 | route: the io thread reads the up channel of an output and writes a down channel of an input. Not the memory map — the CM4 reaches the GPIO and timers; the io thread stays each point's one owner |
| a SOME/IP signal sent or received by an FB | ✅ | ❌ | REQ-PLACE-011 | route: the eth thread reads and writes the channels, as the comm thread does for CAN |
| a bus owned by the satellite core | — | ❌ | REQ-PLACE-012 | route: a comm thread generated in the satellite's image; its signals reach owner FBs as up channels and come from them as down channels |
| the UDS server: 0x28 communication control, NM bus-sleep gating of an FB's sends | ✅ | ✅ | — | the satellite FB keeps running; only the bus send is gated, as for an owner FB |
| FB trace records (`[trace] level = "all"`), two-core dump | ✅ | ✅ | — | generated per core, one timeline in blobly_net |
| an FB's load in `CpuLoad` | ✅ | ⚠️ | — | the FB threads only, not the comm thread or ISRs; a multi-thread satellite reports its first thread only |

Not placement gaps — refused on **every** core, listed so they are not mistaken for one:

- E2E or SecOC on a frame the comm thread **sends**, and TX modes other than cyclic.
- A CAN-FD frame longer than 8 bytes from a system signal (a CAN system signal is one field).
- An FB-to-FB signal between two threads of one partition (the cross-thread IOC fan-out).
- `[[bulk]]` endpoints in an FB — bulk is platform-only by decision.
